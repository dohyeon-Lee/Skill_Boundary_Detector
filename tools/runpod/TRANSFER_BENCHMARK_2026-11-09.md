# FT 평가 파일 전송 검증 — 2026-11-09

이 문서는 당시 전송 측정 기록이다. 이후 SkillVLA PT·FT의 기존 `submit_eval.sh`에
RunPod 입력 준비를 연결했다. 서버에서 `--prepare-runpod`로 평가 YAML을 읽어
필요한 파일을 선택하고, HF 파일을 재사용하거나 없는 입력을 **HF Desk로 업로드**한 뒤
RunPod에서 일반 `submit_eval.sh`로 다운로드·평가한다. 아래 시간은 새 기능 전체의
실행 시간을 측정한 값이 아니다.

현재 FT 평가 설정에서 선택한 **57개 파일, 13.822 GiB**를
연구실 node100에서 RunPod로 준비하고, 모든 파일의 SHA-256을 원본과 비교했다.
대상은 VSA 50k (`dual_bottleneck_pi05vlm_9_9_50k`), Predictor 2k, Terminator 20k,
LIBERO 데이터, FSQ, DINO 및 tokenizer다. 기존 평가 프로세스와 설정은 변경하지 않았다.

## 측정 결과

| 측정 | 대상 | 시간 |
| --- | --- | --- |
| 혼합: HF 다운로드·SHA-256 | 49개 파일, 7.254 GiB | 31초 |
| 혼합: VSA 직접 전송·SHA-256 | VSA 가중치, 약 6.57 GiB | 8분 44초 |
| 혼합: 전체 파일 준비·검증 | 57개 파일, 13.822 GiB | **8분 47초** |
| VSA 최초 비공개 HF 업로드 | 7개 파일, 6.568 GiB | 13분 18초 |
| 모델·데이터 전체 HF 다운로드·SHA-256 | 56개 파일, 13.822 GiB | 42초 |
| 전체 HF: 설정 파일까지 준비·검증 | 57개 파일 | **49초** |
| 최초 VSA 업로드 + 전체 파일 준비 | 측정 단계 합계 | **14분 7초** |

혼합 측정은 HF와 직접 전송을 동시에 실행했다. 작은 평가 YAML도 함께 복사했다.
전체 HF 측정에서도 평가 YAML 1개는 연구실 서버에서 직접 복사했다. 표의 HF 다운로드
대상은 모델·데이터 56개이며, VSA를 제외한 기존 HF 파일은 재업로드하지 않았다.

대상 폴더와 HF 캐시를 각각 새로 만들어 측정했다. SDK 설치, 평가용 환경 설치,
실제 rollout 및 처음 원본 해시·전송 목록을 만드는 시간은 다운로드 측정에서 제외했다.
HF 리비전을 고정했고, 파일명뿐 아니라 Git blob/LFS 해시를 원본과 대조한 뒤 선택했다.
업로드와 파일 준비의 합계는 두 측정 단계의 합이다. 검증 중 작업 폴더 초기화 재시도와
작은 파일 1개의 일시적 HTTP 오류 조사에 쓴 대기 시간은 제외했다. 이 대기를 포함한
전체 실험 벽시계 시간은 22분 42초였다.
최종 HF 측정에는 일시적인 HTTP 통신 오류를 최대 3회 재시도하는 처리를 포함했다.

## 전송 경로와 검증

- Pod는 Community V100 16GB 1장, 컨테이너 디스크 30GB였다. GPU 비용은 생성 당시
  API 표시 기준 $0.19/시간이다. GPU 계산은 실행하지 않았다.
- 연구실 서버 → Pod의 직접 SSH와 rsync는 동작했다. 긴 SSH 전송은 이 환경에서
  재전송·속도 저하가 발생했으며, RunPod CLI의 `send/receive` 경로로 전환했다.
  약 3.27 GiB의 남은 패키지는 약 5분에 도착했고 패키지 및 복원한 원본 해시가 일치했다.
- 첫 전체 직접 전송 검증은 조사·재시도·전송 방식 변경을 포함했으므로 그 총 소요 시간을
  동일 조건의 순수 전송 성능으로 비교하지 않았다. 57개 파일의 최종 SHA-256은 모두 일치했다.
- 첫 직접 전송을 다시 실행했을 때 실제 파일 재전송은 0개, 확인 시간은
  3.324초였다. 혼합 결과의 검증 영수증과 파일 상태를 재확인했을 때는
  2.920초, 전체 HF 결과에서는 3.140초였고
  모델·데이터 재전송은 모두 0바이트였다. 이는 같은 Pod에 파일을 유지하는 경우의 결과다.
- 컨테이너 디스크만 사용한 Pod를 삭제하면 파일도 없어지므로 새 Pod에서는 다시 준비해야 한다.

## 비공개 HF 검증 사본

VSA 업로드는 사용자가 승인한 기존 **비공개 dataset 저장소**의 새 경로에만 추가했다.
공개 체크포인트 저장소에는 올리지 않았고, 기존 HF 경로를 덮어쓰지 않았다.
업로드 후 Git/LFS 메타데이터와 다운로드한 파일의 SHA-256 모두 원본과 일치했다.

- [비공개 VSA 검증 사본](https://huggingface.co/datasets/Dohyeon-Lee-02/SkillVLA/tree/27d92d40195d44a2fbfb01ad7605bdd8075b15c5/runpod_transfer_benchmarks/vsa_50k/17b86dd250a9b071/20261109-075808/pretrained_model)
- 리비전: `27d92d40195d44a2fbfb01ad7605bdd8075b15c5`

이 사본은 향후 재사용할 수 있도록 HF에 보관한다. 테스트 Pod는 검증 후 삭제했고,
남은 Pod는 0개다. node100의 SSH 설정도 검증 전 상태로 복원했다.

## 적용 범위

이번에는 파일 선택·전송·동일성·캐시 재사용을 실측했다. FT 평가 자체는 새 Pod에서
실행하지 않았으며, 평가 환경 및 충분한 VRAM은 별도로 준비해야 한다.
벤치마크용 HF 우선/직접 전송 코드는 `.cache/runpod_checks/`의 검증 도구다.
기존 `submit_eval.sh`에 자동 전송 기능을 연결한 상태는 아니다.

검증 중 `runpod_ssh.sh`가 목록 API에서 직접 SSH 주소를 받지 못하는 문제도 수정했다.
선택한 Pod를 개별 조회하면 주소가 제공되는 실제 응답을 확인했고, 회귀 테스트 37개가 통과했다.

로컬 상세 기록은 `.cache/runpod_checks/direct-transfer-20261109-065316/`의
`manifest.json`, `verification.json`, `hybrid-result.json`, `private-upload-result.json`,
`allhf-result.json`이다. 인증 토큰 및 원본 모델 바이너리는 이 문서에 포함하지 않는다.
