# FT evaluation

`submit_eval.sh` + `ft_eval_config.yaml` run the existing simulator evaluation,
with results under `outputs/`.

All simulator evaluation configurations share **`ft_eval_config.yaml`**. Set
`models`, Predictor and Terminator selectors, thresholds, oracle settings and a
distinct `output_name` there. The default is dual-bottleneck FT **50k**, preskill
UV Predictor FT **2k**, `none_both` Terminator FT **20k**, threshold **0.3**, ten
LIBERO tasks and ten episodes per task. One GPU and one worker are selected for
sharing the held B200; editing this file does not itself launch an evaluation.
The experiment-specific YAML copies have been removed; the evaluator and all
model/checkpoint sweep and diagnostic options remain available in this file.

To repeat the former dual-bottleneck 30k run, change that model's
`vsa_checkpoint` to `"030000"`, its label to `dual_bottleneck_pi05vlm_9_9_30k`,
and the output name to
`ft_dual_bottleneck_pi05vlm_9_9_30k_fullvlm_preskill_2k_noneboth20k_10eps_th03`.
To evaluate Vanilla FT 50k, use this `vsa_dir` in the same `models` entry:

```yaml
vsa_dir: bs16_libero_90_full_full_FSQ333_contrastive_2000_pt_grounded_fov_new_vanila_last_pi05vlm_9_9_vlast9_base_100k_libero_10_full_1_ft_bs16_frozenexpert_dino_own_fullloss
vsa_checkpoint: "050000"
```

Use label `vanila_last_pi05vlm_9_9_50k` and output name
`ft_vanila_last_pi05vlm_9_9_fromPT100k_frozenexpert_50k_fullvlm_preskill_2k_noneboth20k_10eps_th03`.
Predictor, Terminator, scene protocol and the remaining settings stay the same.
Scheduler, QoS and node selection come from the global server profile rather than
server-specific overrides in experiment files.
Offline Predictor evaluation uses `ft_pred_eval_config.yaml` with
`submit_pred_eval.sh`. Set `input_mode: initial_frames` for captured-scene
previews, or use `input_mode: dataset`, `dataset.first_skill_only: true` and
`projected_pixel_metrics: true` for the first-skill XYZ/UV pixel comparison.
Choose XYZ and UV checkpoint entries in `models`; change `output_name` when
switching the input mode, model set or metric protocol.

## Predictor FT evaluation on the same scenes as pi05

Set top-level `initial_state_bank` to a generated pi05
`initial_state_banks/.../eval_init_states.npz`. No new placements are sampled:
every panel restores that archive's sorted episode states and fixture model-body
poses, followed by the usual ten settling steps. The archive must cover the
requested suite, task IDs and episode count; incomplete banks fail, not drop tasks.
For a ten-task comparison, use the ten-task bank created by the initial-frame
capture, not a pi05 worker bank containing only two tasks. Banks generated by
pi05 workers and capture use the same per-task/episode sampling protocol.

Only predictor-provided skills, any required UV/XYZ, and learned termination
are accepted. Set `oracle.episode_exact`, `repeat_episodes`, and
`broadcast_single_episode` to false. GT diagnostics, hindsight oracle latents,
and the task0 demo-reference intervention are rejected too. Synthetic reference
placeholders are used internally; no demo skill/UV/XYZ/timing is loaded for the
rollout. `gt_dataset` may remain for checkpoint/FSQ metadata and HTML training
examples; it is not used to choose rollout conditions in this mode.

Use the same `ft_eval_config.yaml`. Select the desired VSA/Predictor/Terminator
checkpoints in `models`, set `model_defaults.focus_source: predictor`, configure
the three oracle flags above, and set `initial_state_bank` plus a distinct
`output_name`. The task0 intervention must remain disabled. Then submit:

```bash
./submit_eval.sh
```

Global QoS/partitions still apply. Output folders gain `_range2_bank<hash>`;
the path and full archive hash are embedded in panel specs/resume signatures.
Workers recheck the bytes before loading, so editing/replacing a bank cannot
silently reuse stale results. For another scale, point to that generated bank;
the archive metadata, not a separate SkillVLA `random_range` setting, controls
the scene distribution. Switching models does not change the scenes.

The optional task0 diagnostic compares the `learnable_wovis` FT 3k checkpoint
under four conditions: baseline, reference skill only, reference UV only, and
both. This uses the same `ft_eval_config.yaml` and `./submit_eval.sh`; no separate
experiment YAML is needed. To run it, replace that file's contents with the
following configuration. This changes the diagnostic conditions, so keep its
separate `output_name`.

Takeover is armed after the alphabet soup's BDDL `in` predicate is true AND
fingerpad grasp is false for three consecutive observations, while tomato sauce
is still outside. It starts at the **next accepted existing learned boundary**;
no GT timer, forced transition, new reset, extra action or Terminator replacement
is introduced. Untouched evaluations never query this privileged context.

This is **not exact per-rollout GT**: demo-derived reference phases follow successful
FT `demo_12` after its first-can release. The reference **EEF endpoint**, not an
object-centre pixel, is transformed from an object-local frame into the live
world and projected with the live agentview calibration. UV remains latched
within each accepted skill. Reference phases advance only at accepted boundaries;
rejected same-code transitions do not consume phases, and the final phase is held.
If the first reference skill is already active when the trigger is confirmed,
the next learned boundary aligns to the following reference phase; this is logged.
This finite reference program may not provide the right recovery skill for every
off-demo state. Do not interpret a negative result as proving VSA failure alone.

`references/task0_demo12_eef_reference.json` saves the source, FSQ identity,
phase codes, object anchors and endpoint offsets. Its UV targets are checked
against the dataset archive; recorded simulator/processed EEF discrepancies are
retained for audit. The snapshot is hash-identified in resume signatures, so edits
invalidate old caches. To regenerate from the repository root, using CPU only:

```bash
MUJOCO_GL=egl PYTHONPATH=lerobot/src .venv/bin/python \
  lerobot/examples/libero/configs/train_skillVLA/PT/eval/src/prepare_task0_reference.py \
  --run dataset_filtered/skillvla_dataset/libero_10_full_1/FSQ333_contrastive_2000_ft_own_grounded_fov_rand \
  --original libero_original_dataset/libero_10 \
  --output /tmp/task0_reference.json
```

Per-task metrics include `task0_intervention_episodes` and
`task0_intervention_summary`: first-can trigger, delay to the first accepted
boundary, raw/applied skill and UV, retargeted world endpoint, changed-condition
flags and same-skill rejections. Compare full-task success **and** trigger/actual
intervention coverage; episodes that never finish the first can are not tests of
second-can correction. Labels intentionally say `reference`, not `GT`.

## Offline Predictor evaluation

`submit_pred_eval.sh` + `ft_pred_eval_config.yaml` evaluate the Predictor alone,
without constructing a VSA, Terminator, LIBERO environment, or MuJoCo renderer.

```bash
./submit_pred_eval.sh --dry-run  # validate dataset/checkpoints; no model loading or submission
./submit_pred_eval.sh           # checkpoint-parallel GPU jobs; repository .venv selected automatically
```

Set `output_name` at the top of `ft_pred_eval_config.yaml` to choose the report
folder (a single name, not a path):

```yaml
output_name: predictor_fullvlm_eval
resume: true
```

This writes to `outputs_predictor/predictor_fullvlm_eval/`. Keep the same name to
resume the same experiment; use a different name for another experiment. Existing
reports are not renamed when this setting changes.

### Grouped rollout videos (`outputs/`)

New annotated videos share the PT evaluator's three-panel layout: cyan input
UV on Top input only; auxiliary bottleneck XYZ crosses and Top patch boxes on
Rollout (Upper coral / Lower purple for dual bottlenecks). Wrist is unchanged.
This automatically captures existing features during action inference without
another vision forward. See `../../PT/eval/README.md` for capture/geometry details.

FT rollout results are physically split by model, training condition, evaluation
input and checkpoint. Open `outputs/index.html` to browse. Each result contains
only that model's annotated/presentation videos, filtered metrics, a single-model
success-rate plot and skill traces. Only saved video episodes appear; a missing
video does not imply a missing evaluated episode.
Pretrained-VLM results live under `pi05vlm/denoising_wovis/{with_uv,no_uv}/`,
`pi05vlm/vanilla_9_9/`, and `pi05vlm/dual_bottleneck_9_9/`. Vanilla FT
`5k`, `10k`, `30k` and dual-bottleneck FT `5k`, `10k`, `20k` are separate
checkpoint directories, even if the original job evaluated them together.
DINO families likewise have one subdirectory per model variant. x2 initial
state evaluation is isolated under `.../pred_preskill/random_range2/`.

`outputs/analysis/index.html` collects checkpoint trend reports. Each model's
checkpoint parent also has `analysis/index.html`: overall SR vs FT step and
per-task SR lines across checkpoints, including results originally evaluated
in different jobs. Family-level reports compare overall SR across models.
Predictor/terminator, seed, oracle, boundary, training setting and x2 range
protocols remain separate. A single checkpoint is tabulated without inventing
a trend; missing tasks are not filled with zero. Refresh these reports alone:

```bash
python src/build_checkpoint_analysis.py
```

`model_results.json` records the individual results. Original mixed-run metrics,
side-by-side videos, plots and resume caches are preserved in `.evaluation_runs/`.
Its panel aliases point to the real model directories, preserving evaluator
resume without duplicating media. This hidden archive is not the browsing layout.
`Prev/` and `ablation/` remain unchanged. Offline Predictor reports below use
the separate `outputs_predictor/` directory, which is not reorganized.

`outputs/output_locations.json` maps the original YAML `output_name` to the
hidden source run. The shared evaluation resolver honors this mapping, so
resubmission/resume finds the existing results without recreating mixed folders.
Keep this registry with the results. Stored JSON media paths are mechanically
updated; success metrics and media bytes are not changed. New, unmapped output
names retain the usual flat output behavior. To organize recognized new runs
and refresh the local video indexes (only when no evaluation is writing there):

```bash
python src/split_model_outputs.py          # preview only
python src/split_model_outputs.py --apply
```

### Previous-skill input

```yaml
preskill_source: predicted   # gt | predicted (default when absent: gt)
```

`gt` retains the original teacher-forced evaluation: each skill start receives
the preceding GT FSQ code from its own episode. `predicted` instead starts at
BOS (`-1`) and feeds each prediction into the next skill start, strictly in
episode order. Every episode/checkpoint starts a separate history; there is no
GT fallback after a wrong prediction. Models without a preskill condition ignore
this input. Observations, canonical skill-start boundaries and scoring targets
remain the recorded per-episode GT. This is **not** simulator rollout evaluation,
and no single-episode GT broadcast is applied.

Predicted history uses one observation per inference call even when `batch_size`
is larger, because adjacent skill orders depend on each other. GPU parallelism
across checkpoint panels is unchanged. Reports/CSV record `preskill_source` and
`previous_skill_input`; the signature prevents resuming a GT report as predicted
(or vice versa). Use a distinct `output_name` for the two conditions. Partial
resume restores history from completed predecessors and recomputes cached
successors whose actual previous input no longer matches; it never guesses GT
to fill a missing prediction. Legacy GT-only reports remain resumable.

### UV-only Predictors

UV-only checkpoints are supported, including `mode3` / `mode3_preskill`.
The saved heads select the evaluation target automatically: XYZ when an
end-state head exists; otherwise UV when the focus-UV head is enabled.
UV evaluation requires the dataset run's `skill_focus_uv.npz`. Targets are
joined by `(episode_id, skill_index)` with boundary/task checks, not row order.
Mode3 uses one deterministic center crop and one shared VLM pass, then restores
both GT-skill-conditioned and predicted-skill-conditioned UV to the **original
agentview frame** before scoring. `preskill_source` works for both XYZ and UV.

UV reports contain skill accuracy, normalized UV L2/axis MAE and pixel L2
(mean/median/p95; pixel scale uses the archive width/height). These are **not
rollout success rates**. Clipped GT targets are retained, matching UVclip training;
clipped/valid counts are reported. Predictions are never clipped for metrics.
Overlays clip only marker positions to the image border and mark offscreen
predictions. No XYZ head, camera calibration, original HDF5 or simulator is needed
for UV overlays. Reports include the same task/skill-order/demo filters, CSV/JSONL,
per-sample resume and GPU checkpoint sharding as XYZ evaluation.

### Multiple GPUs

```yaml
eval_num_gpus: 5   # upper bound; one Predictor process per GPU
```

Model/checkpoint panels are split evenly across at most this many GPUs. Five
checkpoints with a limit of five request five one-GPU workers; with a limit of
two, the workers evaluate three and two checkpoints sequentially. Extra GPUs
beyond the number of panels are never requested. The default for older YAMLs
without this field is one GPU. `slurm.cpus`, memory and `cpu_threads` are per worker.

On Slurm this uses an array: each element can start when one GPU becomes available,
even on different nodes. Logs are `logs/FTpred_<array-job>_<worker>.out/.err`.
With `scheduler: local`, separate detached one-GPU jobs are launched through the
existing GPU allocator; there must be enough free GPUs (otherwise submission can
stop after launching some workers). `--local` is the manual, sequential one-GPU
path regardless of `eval_num_gpus`. `device: cpu` always uses one CPU worker.

All workers use exactly the same selected examples and checkpoint-owned
preprocessing. Per-checkpoint outputs and resume caches are unchanged. You may
resume with another GPU count without recomputing completed samples. Completed
panels are published with `completion.json`; the root `index.html` is atomically
rebuilt under a shared lock, so the last worker cannot discard another worker's
links. The overview shows completed and pending/running panels; refresh it while
the evaluation runs. No separate GPU/merge job is needed.

Results are separate:

```text
FT/eval/outputs_predictor/<output_name>/
  index.html
  selected_samples.json
  resolved_config.json
  <model-and-checkpoint>/
    index.html
    metrics.json
    predictions.csv
    predictions.jsonl
    images/
    records/                    # per-sample resume cache
```

Open `index.html`, then a checkpoint report. Each skill-start example shows both
recorded camera inputs, GT/predicted FSQ code and coordinates, correctness, and
GT / predicted-skill / GT-skill-conditioned coordinates (XYZ or UV).
The top-camera overlay uses green for GT, red for predicted-skill coordinates, and orange
for GT-skill-conditioned coordinates. Task tabs default to the first task instead of mixing
all tasks. Examples are sorted by task, episode, then skill. Each selected task
shows its own accuracy/coordinate-error summary; demo-split and wrong-skill filters can be
combined, and `All tasks` remains available. The task summary uses all examples in
that task, while the visible-sample counter reflects the additional filters.
Use `Skill order` → `Skill 0` to compare only the first skill across episodes in
the selected task (this is episode position, **not** FSQ code 0). Other skill
indices and `All skill orders` are supported too. This combines with the demo
split and wrong-skill filters. Changing task keeps the selected skill index if
available; otherwise it resets to all skill orders. The task summary remains
the full-task summary, not the accuracy of the filtered subset.

Refresh existing reports without loading a model, re-evaluating, or changing any
predictions/metrics/images (run from this `eval` directory):

```bash
./submit_pred_eval.sh --refresh-reports outputs_predictor/predictor_offline_preskill_ptstats
```

The default data source is the **completed** `libero_10_full_full` SkillVLA build;
its oracle map alone does not contain the labels. **Training demos are included.**
`training_sources: [libero_10_full_1]` only identifies the original training demos
by `(scene_file, demo)`, not local episode number. The report separately summarizes
training and held-out demos and can filter either group. The same examples are
used for every checkpoint. Held-out means unseen **demo occurrences**, not
necessarily unseen FSQ code IDs. `episodes_per_task: 0` evaluates all episodes;
a positive limit samples deterministically and may omit the training example.

Only canonical skill starts are sampled; there is no transition jitter. The GT
endpoint follows `min(frame_end, episode_length - 1)`, matching the dataset builder.
Checkpoint-owned image/prompt/state normalization is retained; already-grounded
dataset states are not grounded a second time. XYZ targets and predictions remain
in the dataset's physical, episode-grounded coordinates (errors are saved in metres
and displayed in centimetres). Projection uses recorded camera calibration, not a
newly rendered scene; old datasets can use their original HDF5 camera XML plus the
action-aligned original episode-start EEF XYZ as a fallback (the same origin used
by the dataset builder, without MuJoCo initialization).

For an FT run, `predictor_checkpoint: "000000"` is a **PT zero-shot** panel: both
weights and preprocessing come from the original PT checkpoint recorded in the
FT config. Saved FT-zero statistics are not used. The PT source is relocated by
run name/checkpoint when evaluating on another server and must be available in
full; missing PT artifacts cause an error, not an FT-zero fallback. Later FT
checkpoints retain their own saved preprocessing. This does not change training
or simulator evaluation. `training_sources` still marks the **FT-reference**
training demos, including in the PT zero-shot panel; it is not PT training membership.

Preskill models use the selected `preskill_source` and first-skill BOS. `gt` is
teacher forcing; `predicted` exposes accumulated prediction-history errors on the
recorded skill starts. Neither is a simulator success rate. `mode2` has no
skill-conditioned XYZ reader, so its two XYZ predictions should coincide.

`device: cpu` uses float32 and requests `slurm_cpu` rather than a GPU allocation.
It is supported, but a large VLM makes CPU inference slow and RAM-intensive; GPU
is recommended. `--local` runs directly instead of submitting: use a compute node,
not a shared login node. The launcher never silently falls back from CUDA to CPU.

`resume: true` skips completed samples with matching dataset, checkpoint, device
and visualization signatures. Changed evaluation inputs require another
`output_name`; results from incompatible settings are never silently mixed.
